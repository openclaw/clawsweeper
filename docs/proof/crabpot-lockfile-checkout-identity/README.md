# Lockfile pnpm materializes on a lockfile-less target repo misread as a checkout mutation

Production run [`32812081965`](https://github.com/openclaw/clawsweeper/actions/runs/32812081965) (`automerge-openclaw-crabpot-283`, `Execute credited fix artifact` step) failed with `target dependency setup mutated checkout identity: contentTreeSha, status, worktreeSha256`, thrown from `assertValidationSourceIdentity` right after `prepareTargetToolchain`'s pnpm install. The same job retried five times over six hours against the identical `source_head`, failing identically every time, no flakiness ([issue #1243](https://github.com/openclaw/clawsweeper/issues/1243)).

`openclaw/crabpot` has empty `dependencies`/`devDependencies` and no `pnpm-lock.yaml` committed. `pnpm install --frozen-lockfile` doesn't error against a repo with no lockfile to freeze; it silently writes one. `validationSourceIdentity`'s `worktreeSha256` and `contentTreeSha` both fold in untracked files (`git ls-files --others --exclude-standard`), so that newly-created, non-ignored file reads as a real checkout mutation and the guard fails closed. Confirmed by directly cloning `openclaw/crabpot` at the failing commit and running `pnpm install` with ClawSweeper's exact install flags: clean tree before, one untracked `pnpm-lock.yaml` after.

**Fix**: capture the pre-install lockfile state (`captureTargetFile`, an existing helper already used for the outdated-lockfile fallback path) and, only when that snapshot records the lockfile as absent, remove whatever pnpm just wrote before the post-install identity check runs. A lockfile that was already tracked or already present untracked is left untouched by this new path, `--frozen-lockfile` already guarantees those cases don't change, and the existing fallback logic for a genuinely outdated lockfile is unaffected. Regression coverage in `test/repair/target-validation.test.ts` proves all three states: absent (new test), pre-existing untracked (existing sibling test), and tracked mutation still fails closed (existing sibling test).

The executable contract is in [`behavior-contract.md`](behavior-contract.md), RED/GREEN evidence is in [`red-green.md`](red-green.md), and [`run-proof.sh`](run-proof.sh) is the Docker-backed Crabbox launcher, executed literally end to end inside the lease, not just copy-pasted piecemeal. [`receipt.json`](receipt.json) binds the head that was actually exercised, `f1cb0dfa666584da87cdf34f80f89fff2b99cc4d` (the fix and its tests; this proof directory was added in a later commit on the same branch that changes no tested file), provider `local-container`, lease `cbx_3e31cb90a5dd` (`coral-krill`), Docker image `node:24-bookworm@sha256:934240a162082fd8b8a2f90cd5114446443f1eba1c5378f6687167ca405e6584`, the full focused `test/repair/target-validation.test.ts` suite (203 passing, 3 skipped for a documented kernel-capability gate unrelated to this change, 0 failing), clean `format:check`, clean `lint`, clean `build:all`.

**Environment note on the production RED/GREEN comparison**: this bug's own code path only runs inside `runContainedCommand`'s Linux namespace containment, which this specific Docker-backed `local-container` lease can't itself nest (confirmed symmetrically: both unfixed and fixed code hit the identical `validation process containment failed: stage=namespace_setup` wall inside the lease, see `red-green.md`). So the actual before/after bug reproduction against the real `openclaw/crabpot@0cb363fdae97a06cc91f96525529cb3907ae20ad` checkout was run directly against a toolchain with working namespace/Landlock support instead, same compiled `dist/repair/target-validation.js`, same real target commit. Everything else (the focused unit suite, format, lint, build) ran inside the Crabbox lease itself and is reported in full above.

**Scope note**: this proof does not run the full `pnpm run check` gate, for the same reason as the prior `lockfile-deprecated-field-network-policy` proof (`test:coverage:no-build` needs CI-only secrets, unrelated to the changed surface). Per `CONTRIBUTING.md`'s guidance to use the narrowest meaningful validation for the changed surface, this proof scopes to build, lint, format, the full test file the change lives in, and the production real-behavior proof.

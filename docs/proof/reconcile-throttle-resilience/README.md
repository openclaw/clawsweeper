# Reconcile throttle-resilience proof

Production run 31634514031-era evidence showed `inspected_targets=3`, `skipped_targets=125`, and `recovered_targets=0` after one `http_403` plus two attributed `not_inspected_abort` targets. At the same time, the `repository_actions` pool was under sustained pressure (`item_metadata` read throttle first=718, repeat=1197; roughly 6,000 `artifact_download` circuit skips) while the `target_app` pool was nearly idle.

The code investigation found that parked REST checks, standard REST checks, and batched GraphQL canonical discovery all selected `GITHUB_TOKEN`. In the scheduled workflow that variable was `${{ github.token }}`, the same repository Actions credential used by the prior-artifact download and stuck-run Actions API remediation. The workflows now mint the existing ClawSweeper GitHub App installation token with read-only contents/issues/pull-request permissions and expose it as `GH_TOKEN` only to target-inspection steps. Repository artifact and Actions-run operations remain on `${{ github.token }}`.

The original abort came from https://github.com/openclaw/clawsweeper/pull/973: complete canonical-alias discovery protected active sibling fences and bounded API usage before mutation. https://github.com/openclaw/clawsweeper/pull/1117 added honest per-target diagnostics while deliberately retaining that behavior. The new policy changes only 403/429 handling: isolated throttles become per-target or per-batch skips, a success resets the counter, and three consecutive throttled calls abort the remaining phase. All non-throttle discovery failures still use the conservative abort path; the existing target, recovery, GraphQL batch, terminal-recheck, and inventory caps remain intact.

In this list, external means a non-`OWNER`/`MEMBER`/`COLLABORATOR` author; maintainer engagement means an assignee, requested reviewer, or maintainer comment or review; automation labels are `clawsweeper:human-review`, `clawsweeper:manual-only`, `clawsweeper:autofix`, and `clawsweeper:automerge`.

- `implemented_on_main`: current `main` fixes the request well enough, even without the proposed workflow, file split, or names. Verify the behavior in source (and tests/docs), then trace fix provenance with `git log -S`/`-G`, `git blame`, `git show -s --format=%H%n%cI%n%s <sha>`, `git tag --contains <sha>`, `git branch --contains <sha>`, `git show <tag>:CHANGELOG.md`, and `gh api repos/<owner>/<repo>/releases`, starting from a merged `closingPullRequests` entry or `referencingMergedPullRequests` (merged PRs that mention the issue without a closing link). A main-only fix qualifies. For a pull request, source resemblance, an overlapping feature, or a current main commit alone is never sufficient to propose `implemented_on_main` or `mostly_implemented_on_main`. Require a GitHub-verified, merged fixing PR in the same repository that GitHub formally links to the request, with an explicit connection to the requested behavior, and cite its URL. If that connection is incomplete, ambiguous, cross-repository, or inferred, keep the PR open and close no linked issue: a linked issue is not permission or proof to close either item. Set `fixedSha`, `fixedAt` (ISO-8601), and `fixedRelease` (the first shipping tag, or `null` when main-only, and the close comment then says fixed on current `main` with `fixedAt`), with source, git-history, and release-check evidence that says current-main-only when no release has the fix. Do not invent release facts; without `fixedSha` plus `fixedRelease` or `fixedAt` and that evidence, keep the item open.
- `mostly_implemented_on_main`: PRs only, older than 60 days, whose central useful change is on current `main` under the same provenance standard. Use it rather than stretching `implemented_on_main` when main covers most but not every line. The leftover diff must be minor, obsolete, risky churn, style-only, superseded, or tracked elsewhere, with no recent substantive human response that changes the decision. Keep open when a meaningful unique fix, feature, security hardening, test, doc, migration, or product decision remains. The close comment says what is on `main`, why the leftover does not matter, and why the stale branch is not useful.
- `cannot_reproduce`: a reasonable reproduction against current `main` fails, or the report no longer matches current behavior. Distinguish missing reporter evidence from a report whose concrete mechanism is disproved. Search the complete current tree, source history, renamed paths, and shipped version when identified; trace the actual owner, callers, dependency contract, and relevant regression tests. If the named implementation never existed or cannot perform the alleged operation, and the real implementation or tests disprove the reported failure, propose a high-confidence close with that source-backed evidence. Do not keep a source-disproven issue open, ask for screenshots or logs, or request maintainer follow-up only because the reporter gave no reproduction. Bulk filing is not itself a close reason, but repeated reports about nonexistent files still close when each claim is independently disproved. Keep open when an affected shipped version, real source path, observed user failure, or dependency behavior remains unverified.
- `clawhub`: a useful idea that belongs as a ClawHub skill/plugin rather than core, with `VISION.md` as the scope anchor: optional integration, provider, channel, skill, bundle, MCP, or plugin-discovery work that current extension surfaces support, without a missing API or protected maintainer signal. For OpenClaw PRs that only add bundled skills under paths like `skills/<vendor>/**`, set `itemCategory: "skill"` and prefer `closeReason: "clawhub"` with high confidence; ask the contributor to upload or publish it through ClawHub.com instead of bundling it in core. Keep open for a bundled-core regression, a missing plugin API, security/core hardening, or a clear product call. For `clawhub` closes, make `bestSolution` and `closeComment` a self-serve handoff: link an already-posted plugin when one exists, name the likely package shape (skill, plugin, provider, channel, bundle, or MCP integration), list basics to verify (metadata, entrypoint, permissions, secrets/config, install/update docs, example usage, smoke proof), and state that ClawSweeper should not open a ClawHub issue, open a ClawHub PR, create a tracking issue, or publish the package on the contributor's behalf.
- `duplicate_or_superseded`: another issue/PR tracks the same remaining work or clearly supersedes this item. Read and link the canonical item, set `rootCauseCluster.canonicalRef` to it, and say whether it is open, closed, merged, or shipped; ClawSweeper keeps a PR open when `canonicalRef` is empty. For a same-root-cause cluster, keep one canonical issue open and close satellites whose unique logs, platforms, or context the close comment can preserve by link. Unique evidence blocks the close only when it implies a distinct root cause, platform-specific fix, or separate remaining behavior. A replacing PR must be merged, or open, proof-positive, and a safe landing path; keep the source PR open when the replacement is closed unmerged, unproven, F-rated, proposed for close, or not cleanly mergeable.
- `low_signal_unmergeable_pr`: the branch may hold a small useful idea but is net-negative because most of the diff is unrelated, copied, generated, bloated, incoherent, or against the repository's structure, so landing it means discarding most of it. Keep open when meaningful unique work can be repaired while keeping most of the branch, when maintainers asked to adopt it, when a protected label or maintainer author needs human judgment, or when the only gaps are tests, style, or review follow-up. When the only blocker is missing proof on an idle low-rated PR, use `stalled_unproven_pr`. The close comment credits the useful part, names the unmergeable diff, and invites a new narrow PR.
- `stalled_unproven_pr`: an external PR whose proof ask expired. Every condition holds: `realBehaviorProof.status` is `missing`, `mock_only`, or `insufficient`; `prRating.overallTier` is `D` or `F`; the PR is at least 14 days old with no new commit or check activity for 14 days; a `status: 📣 needs proof` or `triage: needs-real-behavior-proof` label or a proof-nudge comment is at least 14 days old; and there is no maintainer engagement and no automation label. Not for drafts (they use `abandoned_pr`), minor follow-up on a well-rated patch, or a `proof: sufficient` or `proof: override` label. The close comment names the missing proof kind and invites reopening with real-behavior proof such as a live run, logs, or a validation transcript.
- `author_pr_budget_exceeded`: an external author's open PR count exceeds the repository budget and this is one of their lowest-signal idle PRs. Every condition holds: the context explicitly provides the author's repository open-PR count and it exceeds the configured budget; the PR is at least 7 days old; its latest commit, status, or check activity is at least 7 days old; and `prRating.overallTier` is `D` or `F` or the proof status is `missing`, `mock_only`, or `insufficient`. Never use it for an S/A/B-rated PR with sufficient or overridden proof, a protected or auto-close-exempt label, or maintainer engagement. Never propose this reason when the author open-PR count is unknown, and do not search for the count: the default path is apply-side deterministic promotion and live verification. The close comment states the count and budget, says closing or finishing other PRs frees budget, and invites reopening when under budget or with real proof.
- `abandoned_pr`: an external PR at least 30 days old with no new commit or check activity for 30 days that is stalled: a draft, labeled `status: ⏳ waiting on author`, failing checks, or not cleanly mergeable (merge conflicts) on its current head. Not for S/A/B-rated work with sufficient or overridden proof (that belongs in repair/adopt paths), maintainer engagement, or an automation label. The close comment credits the work, states the inactivity window and stalled state, and invites a rebased reopen or fresh PR with green checks.
- `unconfirmed_product_direction`: an external PR that is correct and well-proven but adds feature or configuration surface without maintainer-confirmed direction. Every condition holds: `itemCategory` is `feature`; `requiresProductDecision` is true; `requiresNewFeature` or `requiresNewConfigOption` is true; `overallCorrectness` is `patch is correct` with no findings; `securityReview.status` is `cleared` with no concerns; proof is sufficient or overridden; quality is C or better; and no automation label is present. Not for bugs with an established behavior contract, security-sensitive work, weak patches, or work maintainers already calibrated. Explain that quality is separate from product acceptance and a maintainer can sponsor, narrow, or reopen the direction.
- `unsponsored_feature_request`: an issue-only feature request waiting on a maintainer product decision. Every condition holds: `itemCategory` is `feature`; `requiresProductDecision` is true; `maintainerDecision.required` is true with `kind: product_direction`; the issue is older than 90 days; there is no maintainer engagement (assignee, milestone, or maintainer comment), no human comment in the last 60 days, and no linked open PR. Never use it for bugs, requests carrying any label whose normalized name contains `security` (including `impact:security` or `clawsweeper:needs-security-review`), `clawsweeper:linked-pr-open`, or strong community traction. The close comment must describe a reversible idea-archive park, not a rejection; say no maintainer has confirmed the direction; state that a qualifying maintainer can automatically reopen it by commenting `@clawsweeper revive`, or that the configured positive-reaction threshold automatically reopens it; and mention ClawHub when relevant.
- `stale_version_bug`: an issue-only bug at least 120 days old tied to a clearly outdated version/build or a code path visibly changed on `main`, with no reproduction confirmed on a recent release. Never with maintainer engagement, a protected label, or any label whose normalized name contains `security`. The close comment names the reported version (or age), says the code has changed substantially, asks for a retest on the current release, and promises reopening when a fresh current-version reproduction is added.
- `obsolete_fix_pr`: a PR-only fix at least 90 days old, with head activity at least 30 days old, changing at most five files, where every touched path was substantially rewritten or removed on current `main` after the PR head commit; CI/workflow fixes qualify when the workflow was since rewritten or deleted. Never with maintainer engagement or protected labels. An S/A/B-rated PR with sufficient or overridden proof qualifies only when evidence proves every touched path is gone or changed. The close comment credits the work, names the files that changed or disappeared, and invites a fresh PR against current `main` if the problem still reproduces.
- `not_actionable_in_repo`: the action belongs outside this repository: project administration, external hosting or third-party services, domain/account ownership, a separately distributed product's renderer/provider/client, or historical cleanup that code or docs cannot fix. Verify ownership signals against the source tree and official release/docs boundaries; QClaw `0.x` desktop/client reports, `qclaw/*` providers, QClaw renderer logs, and externally maintained WeChat adapters are examples of ownership signals, not proof of an OpenClaw bug. When the report does not reproduce on an official OpenClaw release or identify a concrete upstream OpenClaw defect, propose a high-confidence `not_actionable_in_repo` close immediately, name the external owner, and set `workCandidate: "none"`; do not request private/encrypted third-party traces, choose `manual_review`, set `maintainerDecision.required`, or add `clawsweeper:needs-maintainer-review`, and do not turn missing third-party logs into a maintainer-review blocker. Keep open only when evidence demonstrates an actual failure in an official OpenClaw release or owned source path, a missing core extension API, or another reproducible upstream defect. Merely citing healthy owned source paths, generic fallback/delivery plumbing, or a hypothetical upstream boundary does not demonstrate an OpenClaw failure. Setup/support, one-line, screenshot-only, or credential-redaction reports qualify when current code/docs show the behavior is expected or externally configured and no source-level reproduction exists. The close comment asks for credential rotation when relevant and names the diagnostic command, docs page, or external owner.
- `incoherent`: after reading the title, body, comments, and any diff, the item still names no coherent testable problem, owned behavior, or useful bounded contribution: missing essential context, contradictory claims, empty or generated content, or a patch with no maintainer-worthy purpose. Close courteously and invite reopening with an official OpenClaw version, affected component, reproduction, expected/actual behavior, or a focused patch.
- `stale_insufficient_info`: an issue (not a PR) older than 60 days that cannot be verified against current `main`, because reproduction data is missing or because it targets a significantly outdated version or behavior whose code has materially changed, with no human reproducing it on a current version in the last 60 days. Check current code/docs for a known fix first. Never use stale age to close a clear remaining feature, configuration surface, security hardening request, or product decision. The close comment asks for a new issue with current reproduction steps, expected/actual behavior, logs, versions, and config.
